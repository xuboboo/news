## 草稿队列故障恢复上线附加项（2026-09-26）

- [ ] 发布时确保 `backend` 与 `ai-worker` 同版本并重建；不启用全局 `task_reject_on_worker_lost`。隔离验收确认 `article_gen_task` 的 prefork `WorkerLostError` 会在父进程按 generation CAS 标记失败，Celery 原任务仍为 `FAILURE`，Redis 不发生即时无限重投。
- [ ] 锁重试耗尽时，只有成功取得与生成任务相同的 PostgreSQL advisory lock 才可立即标记本代 `failed`。仍有活动 owner 时不抢占，生成继续；安排一次 3605 秒后的确认任务（超过配置的 1 小时硬时限），再次检查锁/status/generation。owner 正常完成后确认不会修改 `ready` 稿。
- [ ] `POST /api/v2/drafts/{id}/regenerate` 对已 `failed` 草稿可立即开启下一代，无需等 stale 15 分钟；旧代重复投递不能覆盖新版。
- [ ] 生产 `visibility_timeout` 保持 4 小时；15 秒等缩短值只用于隔离诊断，不代表生产时延承诺。
- [ ] 边界：硬时限可能产生非 `WorkerLostError`；父进程与数据库同时不可用、确认任务不能发布/执行等情况不能保证立即写 `failed`，保留 generating 超时后的 stale 人工/API 重试入口。全局关闭 worker-lost requeue 是为了避免毒任务无限重投。

## 三、`backend/.env` 生产配置（逐项核对）

| 键 | 生产要求 |
| --- | --- |
| `ENVIRONMENT` | **`production`**（最关键：触发启动安全自检，弱默认值直接拒起） |
| `DATABASE_URL` | 使用上述强口令，不得含默认 `hjradar` |
| `ADMIN_TOKEN` | 强随机值（应急后门通道；留空则该通道关闭） |

| `ENABLE_DOCS` | `false`（不公开 /docs /redoc /openapi.json） |
| `CORS_ORIGINS` | 实际前端域名（逗号分隔；勿放开） |
| `ALERT_WEBHOOK_URL` / `ALERT_WEBHOOK_STYLE` | 按需配置告警推送（wecom/dingtalk/feishu/raw）；本次起 .env 直配生效 |

## 附：存储与日志运维节奏（2026-09-19 实测推演）

清理机制已全自动闭环，无需日常操作：容器日志每容器 10m×3 硬顶轮转；每周一 03:30 `auth_cleanup_task` 一趟清四样（过期会话 / 审计日志默认 180 天 / task_run 90 天 / AI 用量流水默认 365 天，后两者保留期可在管理面板热调）；Redis 缓存 45s TTL、Celery 结果 1 天自过期。本机实测：数据库 13MB、Redis 4.6MB、数据卷合计 148MB（embedding 模型占 ~100MB 固定），按当前采集速率一年后全库预计 <1GB。唯一永久增长的是文章/事件/早报档案（设计如此）。

按节奏执行的观察项：

```bash
# 每月一次：记录库大小基线（首次上线即记录）
docker compose exec postgres psql -U hjradar -d hjradar -c "SELECT pg_size_pretty(pg_database_size('hjradar'));"
# 每周一次：备份到容器外（保留 4 份滚动）
docker compose exec -T postgres pg_dump -U hjradar hjradar | gzip > ../backup-hjradar-$(date +%Y%m%d).sql.gz
# 每季度或大版本部署后：回收构建缓存（开发机实测曾积累 2.8GB）
docker builder prune -f
```

宿主机侧：给 pgdata 所在磁盘设 80% 使用率告警（比盯单项指标有效）；文章档案涨到 GB 量级（预计三年以上）再议归档策略，现在做属过度设计。
