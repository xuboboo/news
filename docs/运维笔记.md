# 运维笔记

部署与日常运维中的实操经验，按时间倒序记录。

## 2026-09-10 聚类门槛调参决策：碎片化别动那两个旋钮

**现状**：新门槛（全带级要求跨来源 + 高位带关键词重合 ≥0.1）重建后 177 篇 / 99 事件（96 个单成员）。
**体检结论**（只读统计脚本）：同来源不同事件且 sim≥0.85 共 817 对，其中 kw≥0.2 的 21 对里真同事件
（如 Win11 光标 bug 三部曲、年龄 API 两篇）与 Win11 学院陷阱（kw=0.46/sim=0.963 的不同教程）
**混在一起，关键词无法区分**——这正是"同来源一律不并"的原因，放开必然回流污染。

**决策：保持 0.85 / 0.2 / 0.1 不动**。理由：
- 单来源独家/连报碎成小事件是精度优先的**设计代价**（审计要求宁缺勿滥）；
- `sim_threshold→0.83` 只影响跨来源 0.83~0.85 的边缘对（会放进更多错误对），**对同来源碎片无效**；
- `high_band_kw_floor→0.08` 同理只放宽跨来源，且放入泛词单重合对；
- 自愈机制：单来源事件在第二来源跟进报道后，会被增量聚类/事件级二阶段合并自动并拢（跨来源路径是通的），
  **只有始终独家的事件才保持单成员——这是诚实结果**。

**何时复查**：跑一周后若发现某重大多部分报道持续只有单来源覆盖且明显该聚合，先查它是被门槛挡住
（用上文体检脚本看它的 sim/kw 落在哪个带），再考虑针对性处理；严禁为治碎片化盲目调低两个旋钮。

## 2026-09-10 后续：502 坑已代码化（nginx 动态解析）

上条 502 坑的永久修复已落地：nginx.conf 改用 `resolver 127.0.0.11 valid=30s` + 变量式
`set $backend_upstream http://backend:8000; proxy_pass $backend_upstream;`，每次请求周期性
重解析 upstream。**单独重建 backend/worker 等后端服务不再需要连带重启 nginx**。
（注意：`docker compose up -d --build backend worker ...` 各服务镜像仍是独立构建，
改了 backend 代码后 worker/ai-worker/beat/crawler 也要一并 rebuild——它们共享 ./backend
构建上下文但镜像彼此独立，这是 2026-09 踩过的"逐服务 build"坑。）

## 2026-09-09 单独重建后端服务后 nginx 报 502

**症状**：单独重建 backend/worker 等后端服务（如 `docker compose up -d --build backend`）后，前端/接口全部报 HTTP 502；backend 容器自身 healthy、日志无错误。

**原因**：nginx 对 upstream（`backend` 容器名）只在 **nginx 自己启动时解析一次**。重建后的 backend 容器会分到新的内网 IP，而 nginx 还缓存着旧 IP，转发连接被拒 → 502。compose 的 `depends_on` 只保证启动顺序，**不会**级联重建依赖方（nginx）。

**处置**：二选一——

```bash
# 已踩坑后恢复：重启 nginx 重新解析 upstream
docker compose restart nginx

# 预防：重建后端时顺手带上 nginx，一劳永逸
docker compose up -d --build backend nginx
```

**当日实锤**：backend 重建后 IP 从 `172.18.0.6` 变为 `172.18.0.9`，nginx 健康检查持续 502（`connect() failed (111: Connection refused) ... upstream: "http://172.18.0.6:8000"`），`restart nginx` 后即刻恢复。
