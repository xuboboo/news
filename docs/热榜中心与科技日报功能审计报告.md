# 热榜中心与软件日报功能审计报告

审计日期：2026-09-09  
审计范围：热榜中心、软件日报，以及两者依赖的热度计算、事件聚合、日报生成、历史查询、前端交互、权限和测试覆盖。  
审计方式：代码静态审查、数据库只读核验、登录态 UI 全链路验收、接口/数据口径核对、现有测试回归。

## 一、热榜中心

### 1. 已验证可用能力

- 页面可正常登录访问，默认 24 小时窗口、3 天、7 天和全部窗口均可切换。
- 频道过滤、URL 同步、文章排名、HotScore、AI 摘要展开和文章详情弹窗均可用。
- 当前页面能展示榜单数量、平均分、摘要覆盖率、当前最高热度文章。
- 现有热度公式结构清晰：浏览、评论、点赞、分享加权，再叠加时间衰减。
- 现有 UI 回归观察：24 小时窗口展示 54 篇，全部窗口展示 139 篇；摘要展开和详情交互成功。

### 2. 主要缺陷

#### P1：前端没有使用后端热榜接口，导致接口和页面口径分裂

后端 `/api/v2/hot/board` 使用最近 120 小时的数据计算榜单；前端热榜页面却从 `/articles/latest?limit=400` 取文章后在浏览器内自行过滤和排序。

- 后端接口位置：[routes.py](/E:/news-rader/news/backend/app/api/v2/routes.py:184)
- 前端计算位置：[HotBoard.tsx](/E:/news-rader/news/frontend/src/pages/HotBoard.tsx:65)
- 前端数据引导位置：[client.ts](/E:/news-rader/news/frontend/src/api/client.ts:214)

结果是：同名的“热榜”由两套不同实现产生。接口调用方、页面用户和未来的导出任务可能得到不同榜单，问题难以通过单一接口复现。

#### P1：全量窗口实际上受最新 400 篇上限限制

“全部”窗口不是数据库全量，而是当前前端缓存的最多 400 篇最新文章。当前数据量只有 139 篇，所以暂未触发，但数据增长后会出现文章被静默截断、榜单排名不完整的问题。

#### P1：热度分数的窗口语义不一致

后端归一化最大值使用最近 120 小时的最大原始分；前端再按 24 小时、3 天、7 天过滤，但不会在每个窗口内重新归一化。因此 24 小时榜单的分数并非“24 小时榜内相对分数”，而是相对于 120 小时基准的分数。

涉及代码：[routes.py](/E:/news-rader/news/backend/app/api/v2/routes.py:76)、[hot_score.py](/E:/news-rader/news/backend/app/algorithms/hot_score.py:38)。

#### P2：后端接口只有固定 120 小时窗口，无法表达前端“全部”语义

后端 `/hot/board` 没有窗口参数，前端却提供“全部”选项。即使未来改为调用后端接口，仍需先定义窗口协议，避免前后端继续出现同名不同义。

#### P2：排序缺少稳定的二级排序

前后端主要按 HotScore 降序排序，分数相同或四舍五入相同的文章没有明确按发布时间、文章 ID 等字段稳定排序，刷新时可能产生名次抖动。

#### P2：摘要覆盖率只按摘要文本是否非空判断

前端映射层没有保留完整的 `ai_status`，覆盖率主要依据 `summary_short` 是否有内容；空文本、历史摘要、失败后残留摘要与当前生成状态没有被严格区分。

#### P2：缺少热榜核心算法和窗口集成测试

现有测试能够验证未登录访问被拒绝，但没有针对 HotScore 边界、零互动文章、未来发布时间、窗口过滤、归一化、分页/上限和接口与页面一致性的测试。

### 3. 热度算法评价

当前公式为：

```text
raw = views + comments * 4 + likes * 2 + shares * 6
score = raw * exp(-0.0075 * age_hours)
```

优点是简单、可解释、容易调参；缺点是互动字段的来源可信度、不同来源的量纲差异、重复转载带来的互动偏差，以及窗口内重新归一化问题尚未处理。互动为 0 时使用衰减后的保底分，能够避免完全无分，但需要产品上明确“保底分是否参与正式排名”。

### 4. 热榜整改优先级

1. 统一为单一服务端榜单数据源，页面直接消费带窗口参数的热榜接口。
2. 明确 24 小时、3 天、7 天、全部的时间边界和归一化规则。
3. 增加游标/分页或明确的全量上限提示，禁止静默截断。
4. 加入发布时间和文章 ID 的稳定二级排序。
5. 补充公式单测、接口集成测试和页面接口契约测试。

## 二、软件日报

### 1. 已验证可用能力

- `/report/daily`、日报日期查询、管理员触发生成和日报推送链路结构完整。
- 报告页面可展示期号、北京时间统计窗口、头部热点、快讯、行业变化、频道统计和 AI 成本。
- 快讯可打开详情弹窗，关联事件和原文链接可用。
- “复制 Markdown”和“打印 / 导出 PDF”入口可见，日报页面基本阅读链路正常。
- 当前日报时间窗显示为北京时间前一日 08:00 至当日 08:00，与后端按 UTC 日切分、Celery Asia/Shanghai 08:00 调度的设计一致。
- 当前数据库存在 2026-09-08 第 147 期，包含 43 篇日报文章、5 个热点、8 条快讯和 5 篇头部文章。

### 2. 主要缺陷

#### P0/P1：事件聚合产生明显错误聚类，污染日报头条

当前第 147 期的第二热点被标记为“六人利用 AI…”，但摘要内容同时混入 Arm CEO、豆包博物馆 AI 导览、百度相机和刑事案件等无关主题。该事件当前热度为 27.4，并且已经进入日报头部热点和概览文案。

这不是单个 UI 展示问题，而是上游事件聚合结果直接进入日报生成，造成标题、摘要、行业变化和热点排序一起失真。

日报服务位置：[report_service.py](/E:/news-rader/news/backend/app/services/report_service.py:129)。

#### P1：日报事件的文章数和来源数可能跨越日报日期窗口

日报候选事件先依据“当天至少有一篇文章”入选，但随后统计该事件的完整成员文章和完整来源数。于是报告文案中的“聚合 X 篇报道”不一定代表当天窗口内的 X 篇，而可能包含历史文章。

涉及代码：[report_service.py](/E:/news-rader/news/backend/app/services/report_service.py:112)。

这会直接影响“今日最热”“交叉报道”“来源数”和日报可信度，应改为同时提供“日报窗口内统计”和“事件全生命周期统计”，不要混用。

#### P1：历史日报前端只加载少量日期，历史选择能力不完整

前端初始化只加载前 7 期，日期芯片最多展示 14 个；后端虽支持最多 60/366 个日期查询，但页面没有完整历史分页、搜索或日期选择器。

- 日期加载：[client.ts](/E:/news-rader/news/frontend/src/api/client.ts:319)
- 日期芯片：[DailyReport.tsx](/E:/news-rader/news/frontend/src/pages/DailyReport.tsx:34)

这会导致历史日报存在于数据库，却无法从正常 UI 路径访问。

#### P2：选中日期不进入 URL，分享和刷新会丢失上下文

日报选中日期只保存在页面本地状态。刷新、复制地址或从其他入口返回后，用户无法回到刚才查看的那一期。

#### P2：较上期比较依赖缓存，历史期可能静默缺少对比

页面只在上一期已经被缓存时计算“较上期”，没有统一保证前后两期同时加载，也没有在缺失时明确提示。

#### P2：历史日报中的事件链接指向当前事件，而非报告快照

日报内容保存了事件摘要和统计，但前端事件点击更偏向跳转当前事件详情。若后续事件重聚类、标题更新或成员变化，历史日报点击后看到的内容可能与当时报告不一致。

#### P2：复制失败无用户反馈，自动/手动生成状态没有区分

复制 Markdown 失败时基本静默处理；页面使用“自动生成”语义，但当前报告也可能由管理员手动触发或重生成，界面没有展示触发来源和重生成状态。

#### P2：日报真实生成链路缺少集成测试

现有报告测试主要覆盖文本清洗、概览辅助函数、Markdown 和 webhook payload；没有覆盖日报日期边界、期号递增、事件跨日统计、错误聚类隔离、空日报、未生成日期、生成幂等和推送失败后的数据库状态。

### 3. 当前日报实例核验

当前可见日报概览为：

> 今日最热「Win11 学院…」，聚合 15 篇报道，2 家来源交叉报道。此外，「六人利用 AI…」等热点持续发酵。

该文案表面格式正常，但其中第二热点已经证实为混杂主题，说明日报的排版和生成流程通过，并不代表内容质量通过。当前 AI 成本为 0，符合本地抽取式摘要路径，但页面“AI Worker / AI 摘要”与“0 次调用”之间缺少更清晰的产品解释。

### 4. 软件日报整改优先级

1. 先修复事件聚合：加入主题相似度、实体约束、来源/时间约束和错误聚类隔离；对低置信度事件降级为独立文章，不进入日报头部。
2. 日报统计严格限定在报告窗口内；如需展示事件全生命周期数据，单独命名并单独字段存储。
3. 给日报保存不可变快照：热点标题、摘要、成员文章 ID、统计值和生成版本一并固化。
4. 增加历史日期分页/日期选择器，并把选中日期同步到 URL。
5. 补充日报生成集成测试、跨日边界测试、幂等测试和错误聚类回归样本。
6. 为复制失败、无历史报告、上一期缺失和手动重生成提供明确状态反馈。

## 四、自评依据

### 热榜中心：72/100

基础交互和公式可用性较好，UI 验收通过；但数据源分裂、全量上限和窗口归一化语义会影响核心榜单可信度，因此数据正确性和扩展性扣分明显。

### 软件日报：62/100

日报展示、生成、详情和导出链路基本完整；但错误聚类已经进入正式日报内容，且日报统计存在跨日口径风险，属于内容正确性和发布可信度的高风险问题。

## 五、最终发布建议

当前版本可以用于内部观察和问题定位，不建议把热榜作为严格全量排名，也不建议把软件日报作为无需人工复核的正式资讯产品。建议按“事件聚合正确性 → 日报窗口统计 → 热榜统一数据源 → 历史与测试补齐”的顺序整改。
