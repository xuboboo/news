# 生产环境部署计划

> 制定于 2026-09-19。形态已与负责人确认：**Linux 云服务器 + 域名 HTTPS + GitHub 克隆分发**。
> 部署当天的快速操作卡见 `docs/上线检查单.md`（本文档的浓缩版）；两份配合使用。
> 所有配置参数、端口、清理机制均出自对仓库源码与本机栈的实测核对，非模板臆测。

## 〇、现状与前提

- 代码已就绪：本地仓库领先远端两个提交（安全升级 + CSP 强制 + 检查单），全量验证绿（后端 337 用例 / 前端 13 用例 / pip-audit 清零 / 强制 CSP 实测下发）。
- 部署形态：Docker Compose 单机 9 服务；**TLS 由容器内 nginx 单层终结**——`deploy/` 下已备好生产配置模板并通过 compose 解析验证（端口正确替换为公网 80/443）。
- 单层 TLS 是刻意设计：主配置对 `X-Forwarded-For` 做覆写防伪造（2026-09-09 审计修复），若在宿主机再加一层反代（Nginx/Caddy/LB 终结 TLS），全部审计 IP 会失真为 127.0.0.1。**禁止双层反代**。
- 硬性版本要求：Docker Compose ≥ 2.24（生产模板的 `ports: !override` 依赖该特性；2024 年后的官方安装源均满足，部署时验证）。

## 一、资源规格建议（依据本机实测推演）

| 项 | 最低 | 推荐 | 依据 |
| --- | --- | --- | --- |
| CPU | 2 核 | 4 核 | 常态负载低（采集/聚类/摘要均为轻任务）；镜像构建时段吃 CPU |
| 内存 | 4 GB | 8 GB | embedding ONNX 常驻约 500MB + 5 个 Python 服务 + PG/Redis；本机实测整库 13MB、Redis 4.6MB，数据侧无压力 |
| 磁盘 | 40 GB | 40 GB+ | 镜像 1.6GB + 模型 100MB + 一年数据 <1GB + 构建缓存（季度 `docker builder prune`，本机曾积累 2.8GB） |
| 系统 | Ubuntu 22.04/24.04 LTS 或 Debian 12 | 同左 | beat 定时按北京时间，宿主机需设 Asia/Shanghai |
| 出网带宽 | 5Mbps 起 | 按访问量 | 前端首载 gzip 后约 110KB；爬虫出站流量小 |

## 二、阶段 A：服务器初始化（约 30 分钟）

```bash
# A1 安全基线：SSH 密钥登录（本地下好公钥后改）
sudo sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config && sudo systemctl reload ssh
# A2 时区（beat 的早报 08:00 / 周清理 03:30 均按北京时间）
sudo timedatectl set-timezone Asia/Shanghai
# A3 交换分区 2G（防构建期内存尖峰 OOM）
sudo fallocate -l 2G /swapfile && sudo chmod 600 /swapfile && sudo mkswap /swapfile && sudo swapon /swapfile && echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
# A4 Docker（官方源）+ 版本验证（compose 必须 >= 2.24）
curl -fsSL https://get.docker.com | sudo sh && sudo usermod -aG docker $USER && newgrp docker
docker compose version
```

云安全组：**仅放行 22 / 80 / 443**。443 是唯一业务入口；backend 调试口 18000 保持仅回环（主 compose 已如此），需要时 SSH 隧道访问。

## 三、阶段 B：仓库与域名（可与阶段 A 并行）

1. **GitHub 仓库转 Private**（网页 Settings → Danger Zone → Change visibility；当前实测可匿名 clone，与私有声明冲突）。
2. 本地 `git push` 推上就绪提交。
3. 生产机克隆通道：推荐仓库 **Deploy Key（只读）**——`ssh-keygen -t ed25519` 后把公钥贴进仓库 Deploy Keys；比 PAT 更窄权。
4. 域名 DNS A 记录指向服务器 IP。⚠️ 若用 Cloudflare：本系统审计 IP 与登录限流依赖直连真实 IP，**建议 DNS only（灰云）**；确需橙云代理，上线后须另行配置 nginx `real_ip` 信任 CF 网段，否则审计 IP 全变 CF 节点且限流误伤。

## 四、阶段 C：TLS 证书（约 10 分钟）

首选 Let's Encrypt（免费 + 自动续期）；已有企业证书则直接放到 `deploy/certs/` 跳过本阶段 certbot 部分。

```bash
# 首签（standalone 模式，需端口 80 空闲——即起栈之前做）
sudo apt install -y certbot
sudo certbot certonly --standalone -d <你的域名>
# 证书就位（在项目根目录）
mkdir -p deploy/certs deploy/acme-www
sudo cp /etc/letsencrypt/live/<你的域名>/fullchain.pem deploy/certs/
sudo cp /etc/letsencrypt/live/<你的域名>/privkey.pem  deploy/certs/
sudo chown $USER deploy/certs/*.pem
```

续期（起栈后 webroot 模式，nginx 的 80 口已预留 ACME 路径）：

```bash
# crontab -e 追加：每周一 03:40 续期并热加载
40 3 * * 1 certbot renew --webroot -w /home/<用户>/<项目路径>/deploy/acme-www --quiet && cd /home/<用户>/<项目路径> && docker compose -f docker-compose.yml -f docker-compose.override.yml -f deploy/docker-compose.prod.yml exec -T nginx nginx -s reload
```

## 五、阶段 D：环境配置（约 20 分钟）

```bash
git clone git@github.com:xuboboo/news.git && cd news   # 私有仓库 + deploy key
cp backend/.env.example backend/.env
echo 'POSTGRES_PASSWORD='$(openssl rand -base64 24) > .env   # 口令记下来，下一步要用
```

`backend/.env` 生产关键项（完整逐项说明见 `docs/上线检查单.md` 第三节）：

| 键 | 生产值 |
| --- | --- |
| `ENVIRONMENT` | `production`（触发启动安全自检，弱配置直接拒起） |
| `DATABASE_URL` | 把根 `.env` 的强随机口令替换进去 |
| `ADMIN_TOKEN` | `openssl rand -base64 32` |
| `BOOTSTRAP_ADMIN_EMAIL` / `BOOTSTRAP_ADMIN_PASSWORD` | 首启建号用，首登改密后移除 |
| `COOKIE_SECURE` | `true` |
| `ENABLE_DOCS` | `false` |
| `CORS_ORIGINS` | `https://<你的域名>` |
| `SESSION_TTL_HOURS` | `24` |
| `EMBEDDING_BASE_URL` / `EMBEDDING_MODEL` / `EMBEDDING_API_KEY` / `EMBED_DIM` | `http://embedding:80/v1` / `BAAI/bge-small-zh-v1.5` / `local-embedding` / `384` |
| `AI_URL_ALLOWLIST` | `embedding`（内网向量服务精确豁免 SSRF 校验） |
| `ALERT_WEBHOOK_URL` / `ALERT_WEBHOOK_STYLE` | 按需（本次起 .env 直配已生效） |
| `LLM_*` | 按需（不配则自动用内置抽取式摘要，离线可用） |

生产编排文件就位：

```bash
cp deploy/nginx-prod.conf.example deploy/nginx-prod.conf
cp deploy/docker-compose.prod.yml.example deploy/docker-compose.prod.yml
ls deploy/certs/   # fullchain.pem + privkey.pem 必须在
```

## 六、阶段 E：构建与启动（15–30 分钟，视网络）

```bash
docker compose -f docker-compose.yml -f docker-compose.override.yml \
               -f deploy/docker-compose.prod.yml up -d --build
```

- ⚠️ **必须显式三文件**：`-f` 一旦出现，`docker-compose.override.yml` 不再自动合并，而 embedding 服务定义在 override 里，漏带则向量聚类不可用。
- 首启预期：镜像构建 5–15 分钟（pypi/npm 下载）；embedding 首启经 hf-mirror 下载模型，健康宽限 5 分钟属正常；postgres 首建库约 1 分钟。
- **backend 启动报错 = 安全自检生效**（特性而非故障）：按报错项回 `backend/.env` 改对再 `up -d`，自检项为 cookie_secure / enable_docs / admin_no_auth / 默认口令 / 占位密钥。

验收就绪：`docker compose -f docker-compose.yml -f docker-compose.override.yml -f deploy/docker-compose.prod.yml ps` 9 服务全 healthy（crawler 有 5 分钟心跳宽限）。

## 七、阶段 F：上线验收（15 分钟）

1. 冒烟十项按 `docs/上线检查单.md` 第五节执行（登录→强制改密→四个数据页→管理面板全绿→告警测试推送→**浏览器控制台无 CSP 拦截报错**）。
2. HTTPS 专项：
   ```bash
   curl -I https://<域名>/          # 应见 HSTS + 强制 CSP + nosniff 等安全头
   curl -I http://<域名>/           # 应 301 到 https
   ```
   浏览器地址栏锁标 → Cookie 带 Secure；`/docs`、`/openapi.json` 返回 404。
3. 记录基线（此后每月对比）：`docker compose ... exec postgres psql -U hjradar -d hjradar -c "SELECT pg_size_pretty(pg_database_size('hjradar'));"` + `df -h`。

## 八、上线后第一周固化

| 日程 | 动作 |
| --- | --- |
| 当日 | 首登改密完成后，从 `backend/.env` 删除 `BOOTSTRAP_ADMIN_*` 两行并 `up -d --build backend` |
| 第 1 天 | 验证证书续期链路：`certbot renew --dry-run`；观察首轮爬虫数据（起栈 30 分钟内）与次日 08:00 早报 |
| 第 1 周内 | 备份 cron 就位：每周日 `docker compose ... exec -T postgres pg_dump -U hjradar hjradar \| gzip > backup-hjradar-$(date +\%Y\%m\%d).sql.gz`（容器外目录，滚动保留 4 份） |
| 第 1 周内 | 云监控给系统盘设 80% 使用率告警 |
| 每季度 | `docker builder prune -f` 清构建缓存 |

## 九、回滚预案

- **代码回滚**：`git checkout <上一个提交> && docker compose -f ...三文件... up -d --build`；基础镜像 digest 锁定，构建可复现；`pgdata` 卷不受影响。
- **数据回滚**：停 backend → `gunzip -c backup-x.sql.gz | docker compose exec -T postgres psql -U hjradar hjradar` → 重启。
- **配置回滚**：改 `backend/.env` → `up -d --build backend`（backend/worker/ai-worker/beat/crawler 共用镜像一并生效）。
- **证书故障**：优先 `certbot renew --force-renewal` 后热加载；切勿为临时恢复而改回双层反代（会破坏审计 IP）。

## 十、风险与对策（均已结合本系统实际）

| 风险 | 对策 |
| --- | --- |
| 宿主机再套一层反代（常见误区） | 已用单层 TLS 模板规避；运维笔记中明令禁止 |
| Compose < 2.24 时 `!override` 不生效端口冲突 | 阶段 A4 已验证版本；文档标注硬性要求 |
| embedding 首启拉模型慢/失败 | 已配 hf-mirror 镜像 + 300s 健康宽限；失败看 `docker compose logs embedding` |
| Cloudflare 橙云导致审计 IP/限流失真 | 建议 DNS only；确需代理后配 real_ip 网段 |
| 私有仓库影响 CI | GitHub Actions 私有仓库每月 2000 免费分钟，当前流水线每次 <10 分钟，充足 |
| 目标资讯站反爬升级 | 爬虫侧已有站点熔断 + 连败放弃 + 自愈重排（`stats_heal_batch`），告警会推送，人工介入即可 |
| 首启自检报错被当故障 | 属设计行为：报错列表精确对应 .env 键，按提示修配置 |
| Windows 本机与 Linux 生产镜像差异 | 生产机现场 `--build` 重新构建（计划即是如此），不在本机导出镜像搬运 |

## 附：部署当日时间线建议

准备充分时全程约 1.5 小时：A 服务器初始化 30min（可与 B/C 并行）→ D 环境配置 20min → E 构建启动 30min（含模型下载）→ F 验收 15min。建议避开整点上线（爬虫启动即采集，避免与目标站整点高峰重叠无意义；无实质影响，仅习惯）。
