## 一、结论摘要

系统的基础工程能力已经具备：Docker 服务健康，认证、CSRF、RBAC、会话控制、API 基本契约、采集来源映射、前端主要路由均能工作；后端测试、前端构建和 lint 也全部通过。

但当前仍不建议将“事件聚类/日报”作为无人值守的可信事实层直接发布。事件服务在“把新簇并入已有事件”的分支中没有再次校验语义相似度阈值，标题关键词条件可能单独促成错误归并。运行态数据库中已经看到一个包含多个明显无关科技主题的 24 篇事件，说明该风险不是纯理论问题。该问题会向事件详情、热榜、软件日报和后续统计扩散，应作为最高优先级整改项。

## 二、最高优先级问题

### P0：事件并入已有事件缺少语义相似度门槛

位置：[event_service.py](/E:/news-rader/news/backend/app/services/event_service.py:398)

现状：`run_event_clustering` 的已有事件匹配分支会计算 `sim`，但判断条件只有 `sim > best_sim` 和标题关键词 Jaccard 阈值，没有显式要求 `sim >= sim_threshold`。因此，低语义相似度的文章簇只要标题关键词有一定重合，就可能并入错误事件。

运行态证据：数据库中事件 3 的标题为“六人利用 AI‘越狱’生成淫秽物品最终获刑……”，成员数 24，但成员标题同时出现 ARM AI 癌症研究、豆包博物馆、百度摄像机、零点击蠕虫、AI 电力需求、Meta 眼镜、机器人等明显不同主题。该形态符合错误聚类特征。

影响：事件详情、事件数量、热榜关联、软件日报“重点事件”、事件摘要和后续统计均可能被污染；错误事件一旦生成，还会成为后续文章的错误吸附目标。

整改：在该分支强制使用与簇内合并一致的 `similarity_gate_pass`/`sim_threshold` 规则；补充 `run_event_clustering` 的数据库集成测试；对既有事件重新聚类、拆分污染事件并重建受影响日报。修复前应将事件/日报结果标记为需复核，而不是继续扩大数据影响面。

### P1：租户变更后旧会话不会按预期吊销

位置：[users.py](/E:/news-rader/news/backend/app/api/v2/users.py:360)

现状：代码先把 `target.tenant_id` 更新为新租户，再用 `new_tenant != target.tenant_id` 判断是否发生租户变化；比较时两者已经相等，因此租户迁移不会进入会话吊销分支。角色变更和停用用户会吊销会话，但租户迁移不一致。

影响：用户迁移租户后，旧会话仍可继续使用，造成会话生命周期和租户归属语义不一致，尤其不利于管理后台的即时生效预期。

整改：在赋值前保存 `old_tenant_id`，用 `old_tenant_id != new_tenant` 判断并吊销会话；补充“租户迁移后旧 token 失效”的 API 集成测试。

### P1：单来源采集失败被整体记为成功

位置：[multi.py](/E:/news-rader/news/backend/app/crawler/multi.py:37)、任务封装位于 `backend/app/tasks/tasks.py` 与 `backend/app/crawler/loop.py`

现状：多来源采集对单源异常执行 rollback 后继续采集，并返回带有 `per_source.error` 的结果；上层任务没有将该部分失败提升为 failed/degraded 状态，因此任务记录可能显示 success，告警也可能认为任务正常。

影响：IT之家或快科技其中一个来源持续失效时，系统看起来仍“采集成功”，但数据覆盖已经缩水，属于静默部分故障。

整改：区分 `success`、`degraded`、`failed`；只要来源异常，任务明细、状态接口和告警都要显式展示。可继续保留其他来源的成功数据，但不能丢失失败信号。

## 三、后端审计

### 3.1 架构与运行态

优点：FastAPI、SQLAlchemy/PostgreSQL/pgvector、Redis、Celery、爬虫和 AI worker 的职责边界清晰；Docker Compose 中 backend、worker、ai-worker、beat、crawler、embedding、nginx、postgres、redis 均曾处于 healthy；任务锁、超时、重试、节流和来源频道映射均有实现。

风险：事件聚类会加载近期文章并遍历近期事件，近期事件合并还包含近似 O(n²) 的候选比较；当前 139 篇文章规模尚可，但没有看到明确的容量上限、向量候选检索或增长告警。数据量增长后，聚类延迟和数据库压力会随规模放大。

建议：为聚类增加候选窗口、向量索引/近邻召回、单轮处理上限和耗时/候选数指标；超过阈值时进入可观测的 degraded 状态。

### 3.2 认证、授权与安全

优点：登录会话使用随机 token 的 SHA-256 存储，Cookie 使用 HttpOnly/SameSite，存在过期和闲置超时；密码使用 bcrypt；具备登录锁定/IP 限流、CSRF、RBAC、租户会话吊销和审计哈希链。业务 API 默认经过用户依赖保护，健康检查保持公开，前端外链使用 `noopener noreferrer`。

问题：

1. [config.py](/E:/news-rader/news/backend/app/core/config.py:14) 与 [docker-compose.yml](/E:/news-rader/news/docker-compose.yml:15) 提供了数据库、Redis 和 Compose 密码的可运行默认值；`cookie_secure` 默认关闭、OpenAPI docs 默认开启。若部署忘记覆盖环境变量，容易把开发默认值带入生产。
2. [users.py](/E:/news-rader/news/backend/app/api/v2/users.py:360) 存在上文所述的租户迁移旧会话问题。
3. Nginx 有常用安全响应头和缓存策略，但尚未配置 CSP；建议先以 Report-Only 方式收集兼容性，再逐步收紧。
4. 生产镜像仍包含 tests/scripts，见 `backend/Dockerfile`；这会增大镜像并扩大不必要的运行时文件面。

建议：生产环境对关键 secret、`cookie_secure`、docs 开关做 fail-fast 校验；默认拒绝弱密码和空 token；拆分生产镜像与测试镜像；补充 CSP、镜像扫描和启动时安全配置自检。

### 3.3 API 与数据模型

API 只读回归 51/51 通过；数据库检查结果包括：文章 139、事件 38、事件关联 91、日报 1，`null_nid=0`、待处理数据 0、空正文 0、文章向量覆盖 100%，无孤儿事件关联、无空 points/tags。来源频道真实性检查匹配 94、频道不一致 0、可疑项 0。

仍需关注：

- 报表按 UTC 日界线选择数据，而系统业务时区为 Asia/Shanghai；日报的日窗口和事件全量成员统计也存在语义不完全一致的风险。
- 事件/热榜结果依赖聚类正确性；API 契约通过不代表业务数据正确。
- `embedding.py` 的余弦计算对向量维度使用 `zip`，维度不一致时可能静默截断，建议显式拒绝并记录向量指纹。
- 允许 `embedding_strict=false` 时会启用 hash fallback；该运行开关应有明显告警，并阻止不同向量来源无提示地混合进入事件聚类。

### 3.4 任务、爬虫与 AI 流程

外部调用具备超时、成本统计、重试/退避和节流；当前任务记录最近运行均为成功，24 小时失败任务为 0。问题不在基础调用能力，而在部分失败的状态表达：来源异常被吞在结果 detail 中，没有进入统一失败/降级告警链路。

AI 本地模式下摘要和向量覆盖正常，运行态显示 LLM 未配置但本地抽取式摘要/embedding 可用；需要让运营侧明确区分“本地规则生成”和“外部 LLM 生成”，避免把本地结果理解为 LLM 覆盖。

### 3.5 后端测试与可维护性

`python -m pytest tests -q`：147 passed，1 warning。测试覆盖了认证、API、部分事件聚类纯函数和业务服务，但没有覆盖最关键的 `run_event_clustering` 数据库集成路径、租户迁移会话吊销、单来源失败状态传播和日报窗口边界。下一轮测试应优先补这四类。

## 四、前端审计

### 4.1 路由、权限与页面可用性

React 18 + TypeScript + Vite + HashRouter；主要页面 `/latest`、`/events`、`/report`、`/admin`、`/usage`、`/users`、`/audit`、`/account` 均完成登录后只读验收。路由整体由 `RequireAuth` 保护，Usage 有前端超管门槛；后端仍是最终权限边界。

`/admin` 可以显示数据库、Redis、Celery、AI 配置、文章/事件覆盖率和任务状态；`/users`、`/audit`、`/account` 的管理功能入口和状态展示完整。主要问题是冷启动时多个请求并行，页面会短暂显示“后端未连接/自动重连中”，随后又正常加载；这是加载态与离线态混用，不是实际服务故障。

### 4.2 前后端数据联动

位置：[client.ts](/E:/news-rader/news/frontend/src/api/client.ts:214)

现状：前端引导阶段一次取 `/articles/latest?limit=400` 和 `/events?limit=100`，之后每 60 秒刷新并在内存中驱动多个页面；日报历史只加载前 7 条报告。[HotBoard.tsx](/E:/news-rader/news/frontend/src/pages/HotBoard.tsx:65) 主要在客户端计算榜单。

问题：

1. 热榜客户端数据窗口、排序/热度语义可能与后端热榜 API 不一致，页面展示和接口结果存在漂移风险。
2. 固定 400/100 的内存快照不是可持续分页方案；数据量增大时会增大首屏、刷新和浏览器内存压力。
3. 日报接口支持更长历史，但 UI 只缓存有限报告，较旧日期无法自然浏览；前后日报对比在缓存缺失时可能静默缺少。
4. 文章映射会根据非空 summary 计算覆盖率，并未充分使用 `ai_status`；失败、处理中和本地降级结果的展示语义不够明确。

建议：把热榜、事件、日报历史改成服务端分页/窗口 API；统一前后端排序、时间窗和权重定义；日期选择写入 URL；对“加载中、离线、局部降级、数据为空”使用不同状态。

### 4.3 错误处理、交互和安全

优点：Modal 有 Escape、焦点限制和滚动锁；外链打开方式安全；错误边界可避免整页白屏；API bootstrap 失败时不伪造业务数据，降为明确的空状态。

问题：

- [ErrorBoundary.tsx](/E:/news-rader/news/frontend/src/components/ErrorBoundary.tsx:17) 将原始 `error.message` 直接展示，生产环境可能暴露内部实现信息；应展示友好提示和错误编号，详细信息仅写入受控日志。
- 初始化期间的“后端未连接”提示过早出现，多个页面均观察到同类闪烁；应区分 bootstrap loading 和确认离线。
- 管理页面部分使用 `any`，API 返回模型没有完全收敛为共享类型；后端字段变化可能在编译期漏检。
- CSP 尚未配置，建议和 Nginx 安全头一起推进。

### 4.4 前端测试与工程质量

`npm run build` 通过，`npm run lint` 通过；但仓库没有发现前端 `*.test.*`/`*.spec.*` 测试。当前没有自动验证路由权限、API bootstrap、轮询刷新、热榜计算、日报日期切换、Modal 键盘可用性和错误态，因此 build/lint 通过不能代表前端回归安全。

建议至少补充：

1. API client 的 mock contract 测试和 bootstrap 失败/重连测试；
2. HotBoard、Latest、Report 的数据窗口和日期选择测试；
3. Playwright/Cypress 登录后关键路径 E2E；
4. 管理员/普通用户/未登录的路由权限矩阵测试；
5. 生产错误边界、离线提示和局部 API 失败的可视回归。

## 六、整改顺序

### 立即处理

1. 修复 `event_service.py` 的语义相似度门槛缺失；补集成测试。
2. 对既有事件做污染检测、拆分/重聚类，并重建软件日报和相关统计。
3. 修复租户迁移旧会话吊销逻辑，并补权限生命周期测试。
4. 将单来源采集异常改为 `degraded`/`failed` 可观测状态并接入告警。

### 第二阶段

1. 统一热榜服务端 API 与前端窗口/排序语义，消除客户端独立计算漂移。
2. 将文章、事件和日报历史改成分页/按日期窗口加载。
3. 补齐后端集成测试和前端单测/E2E，覆盖认证、事件、日报、轮询和错误态。

### 发布前硬化

1. 生产环境 secret、Cookie、docs 配置强制显式设置，禁止弱默认值。
2. 加 CSP（先 Report-Only），收敛错误边界输出，清理生产镜像中的测试脚本。
3. 为 embedding 维度、模型指纹、聚类耗时、来源级失败率和日报时间窗增加监控。
